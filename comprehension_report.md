## What this document is

A proposed design for "plaps," a single-user, self-hosted photo gallery web app that indexes roughly 150K existing JPEG files in place on a local disk and serves a Google-Photos-style experience: a flat date-sorted timeline, a folder tree view, and genuine semantic search over joint text+image embeddings. The filesystem is the source of truth — the server never copies, moves, renames, or writes originals; it derives only WebP thumbnails and screen-fit images into a cache outside the library, keyed by content hash. The stack is deliberately small: one Python process (Flask served by waitress) with SQLite as the only store for metadata, vectors, and a job queue; pyvips for pixels and piexif for EXIF; a no-build ES-module frontend; lighttpd as reverse proxy and the only authentication layer; and embeddings from llama.cpp running EmbeddingGemma 2 on a separate machine, reached through a single adapter module. The document gives the problem statement, goals, non-goals, eight critical user journeys, a technical plan (component map, process model, SQL schema, scanning/change detection, media serving, embedding pipeline and search, JSON API, security, configuration), alternatives considered with rejection reasons, non-functional requirements, and a file-by-file implementation plan with pinned tuning defaults and a verification plan. It is greenfield: everything is created new.

## What a naive reader would understand it requires

- Index ~150K JPEGs by path with stat-based change detection (path + mtime + size): a stat-pruned polling loop (30 s, backing off to 10 min idle), a daily full stat sweep, and a monthly re-hash pass. Blake2b content hash is a non-unique identity used to re-link moved/renamed files in the same pass, to report duplicates, and to revive tombstones when content reappears within a 30-day purge window. A mass-delete guard halts all tombstone writes when the library root is unstat-able or when unre-linked disappearances exceed 10% of the previous pass's file count, latching a state only clearable via `POST /api/admin/guard/resume`.
- Serve a cursor-paged timeline (opaque keyset cursor over `(date_taken, photo_id)`) with no pagination UI and stable windows under concurrent scanner writes; a folder tree derived at query time from indexed paths, folders sorted by recursive newest date-taken, empty branches hidden; and semantic search that embeds the query text server-side, applies any date/folder filter as a SQL WHERE before ranking, then brute-force cosine-ranks candidates against a resident float32 numpy matrix of L2-normalized vectors for the active model, always returning a coverage count line ("search covers N of M photos") that distinguishes "nothing matched" from "nothing embedded."
- Derive two 512 px thumbnail variants per photo at scan time (square center-crop for the uniform grid, aspect-preserving for justified rows — both always generated, grid style is a user display option) plus ~2048 px screen-fit images generated on demand, all WebP quality 80, stored under a two-hex shard keyed by `(content_hash, variant)` with immutable cache headers. Originals are downloadable by explicit action only, resolved from the database by id, streamed with Range/206 support. X-Sendfile is explicitly rejected as verified-broken on the target lighttpd.
- Run as one process: a 16-thread waitress pool serving the Flask app, with the scanner and embed worker as daemon threads sharing a single locked SQLite writer connection (WAL readers elsewhere). Crash recovery comes from the jobs table and a scan checkpoint in `meta`. If the AI box is down, browsing, folders, and downloads are unaffected, search serves what is embedded with the coverage line visible, and the embed queue backs off and resumes. A model change re-embeds through the same job queue while old-model vectors keep serving, cutting over when new-model coverage crosses a threshold, then deleting old vectors.
- Configure via a single TOML file that refuses cold start without `library_root`; authentication is proxy-level password auth at lighttpd (the only auth layer, consumable by a future Android client); and verify with an API-level pytest suite using a fake embedding adapter, at least 85% branch coverage on the identity/search modules, plus manual end-to-end and performance smoke checks (timeline p95 < 100 ms, search p95 < 50 ms warm).

## Findings

**Major — In-place edit semantics conflict with the schema.** Attaches to CUJ 5 (line 90), Data model key points (line 193), scanner (line 434), and `tests/test_scanner.py` (line 544). "An in-place edit deletes the old record and inserts a new one" cannot mean a tombstone because `path` is UNIQUE — a tombstoned row would block the insert — and the document never says what happens to the old record's `photo_id`, its vector row, or its cache files. One implementer hard-deletes the row (new `photo_id`, immediately removes the old vector and cache orphans); the other updates the row in place (same `photo_id`, cleared stage columns) and leaves the old vector in place until re-embed — which means the edited photo keeps ranking on its pre-edit embedding, and `/original/<photo_id>` links differ in stability.

**Major — The model-cutover coverage threshold is never pinned.** Attaches to CUJ 8 (line 108), embed worker (line 449), and the pinned defaults table (lines 582–591), which omits it. "Cuts over when new-model coverage crosses a threshold" gives no number and no definition of coverage (fraction of live photos? are `failed_perm` photos counted against it?). One implementer cuts over at 50% and excludes failed files from the denominator; another waits for 95% and counts them — materially different points at which partially-re-embedded photos lose search visibility.

**Major — The adapter's load-bearing wire format is delegated to a file outside the document.** Attaches to Embedding pipeline (line 205) and `plaps/embed/adapter.py` (line 444: "payload encoding, batching size, and endpoint path exactly as recorded in the embedding spike"). The document never states the endpoint path or the image payload shape, and the spike it defers to shows that a plausible-but-wrong shape is accepted and silently returns a garbage text-vector. With only this document, one implementer builds the flat OpenAI shape and ships silently wrong embeddings; the other builds the nested `content`-array shape. Related and undecided even in the spike: whether the worker embeds the original bytes or the cached ~2048 px screen-fit image.

**Major — The JSON response bodies are never specified.** Attaches to the API surface table (lines 209–218) and the endpoint modules (lines 461–474). The document calls this API the contract for a future Android client and requires "the same error shape," but never lists the fields of a photo card (the client needs at minimum `photo_id`, `content_hash`, `width`, `height`, `date_taken` to build media URLs and justified-rows layout), nor `limit` defaults/maximums. Two implementers invent different card shapes and the stated Android-client compatibility claim fails.

**Major — `sq` crop is stated two ways.** Attaches to Thumbnail and image serving (line 201: "`crop=Interesting.CENTRE` — verified") versus `plaps/images.py` (line 439: "512×512 smart-crop"), which in pyvips vocabulary means `Interesting.ATTENTION`. One implementer ships center-crop squares; the other ships salience-weighted crops — visibly different grids.

**Major — Grid style and timeline order are "settings" that exist nowhere.** Attaches to Derived images (line 39: grid style "available as a user option") and CUJ 2 (line 72: "newest or oldest first, per setting"). The configuration surface (line 226) lists no such keys and no persistence mechanism is given. One implementer makes these client-side localStorage preferences; the other adds server TOML keys — different config surfaces, different API defaults, and different behavior across devices.

**Major — Coverage-line scope under an active filter is ambiguous.** Attaches to Semantic search goal (line 38), CUJ 4 (line 84), and Embedding pipeline (line 205: counters "come from the same counters `/api/status` publishes"). Global status counters suggest global coverage, but the line's stated purpose — telling "nothing matched" from "nothing embedded" — under a folder filter argues for filter-scoped counts. One implementer returns library-wide N-of-M even when the filtered folder is fully un-embedded (the line then misleads); the other computes coverage within the filter.

**Major — Two sources of truth for `model_id`.** Attaches to Configuration (line 226: `embedding.model_id`) and the adapter/worker (lines 444, 449: `adapter.model_id` compared against `meta.active_model_id`). When the endpoint's actually-served model diverges from the configured one — exactly the CUJ 8 scenario — one implementer stamps vectors from the config value, the other probes the endpoint; the re-embed trigger and vector stamping then disagree.

**Major — Guard-threshold arithmetic is underspecified.** Attaches to Scanning (line 197) and CUJ 7 (lines 98–102), pinned at 10% (line 589). "Unre-linked disappearance count exceeds the threshold of the previous pass's file count" does not say whether "file count" means alive rows or files seen in the walk, whether "previous pass" is the 30-seconds-ago pass or a stable baseline, or how tiny libraries behave (a 10-photo library trips on one deletion). One implementer compares against alive-row count from the last completed pass; the other against the walk count — the same reorganization trips the guard for one and not the other.

**Major — Re-embed job semantics and dedup are unspecified.** Attaches to the `jobs` table (lines 185–187, kinds only `'thumb' | 'embed'`) and the worker (line 449). Nothing states whether `(photo_id, kind)` is unique or how a model-wide re-enqueue coexists with photos that already have pending initial-embed jobs. One implementer adds a uniqueness constraint and treats a pending job as covering the re-embed; the other inserts duplicates and embeds the same photo twice. Adjacent: `embedded_at` is a single per-photo column (line 175) while vectors are per `(photo_id, model_id)`, so its meaning during a re-embed is also ambiguous.

**Major — Screen-fit generation has no owner and no tracking.** Attaches to Thumbnail and image serving (line 201: "generated on demand on first view") and `plaps/api/media.py` (line 479: "`ensure()` on miss"). The jobs table has no `screenfit` kind and `photos` has no `screenfit_at` column, and nothing says whether generation happens synchronously in the request thread (latency, writer-lock interaction) or is enqueued. One implementer generates synchronously in the request; the other enqueues and serves a placeholder until the job completes.

**Nit — Auth method is stated inconsistently.** Overview (line 13), Goals (line 40), and Security (line 222) all say "basic auth," while the NFR (line 362) and the lighttpd sample (line 410) specify digest against the existing htdigest file. The NFR explains the interchangeability, but a reader of the early sections alone configures basic auth.

**Nit — The spike documents are listed as files to create in a greenfield plan that also says they already exist.** Attaches to item 43 (lines 578–580) against the plan's header (line 383: "every file below is created"). One implementer re-runs and rewrites the spikes; the other skips the item as already satisfied.

**Nit — Sorting of unknown-date photos is unspecified.** Attaches to the data model (lines 172–173, `date_source` 'unknown') and the timeline endpoint (line 464). One implementer emits NULL `date_taken` and lets SQLite's NULLs-first ordering place them at one end; the other coalesces to a sentinel so they sort last.

**Nit — Cursor encoding is described two ways.** Line 211 says "opaque base64"; line 464 says "base64url of `'<date_taken>|<photo_id>'`". Opaque-to-client makes this survivable, but the two implementers produce incompatible cursors and different date-string formats inside them.

**Nit — Several config defaults are never pinned.** The defaults table (lines 584–591) covers scanner, tombstone, and thumbnails only; `cache_dir`, `database_path`, `timezone`, and `embedding.batch_size` defaults (line 226) are left to the implementer — e.g., cache defaults to a sibling of the database versus a path relative to the config file; timezone defaults to system-local versus UTC (which changes every mtime-fallback date).

**Nit — "Stall" detection is never defined.** CUJ 1 (line 66) and `static/js/status.js` (line 515) require a "visible error state" / "stalled-scan error banner," but nothing defines a stall. One implementer flags no-checkpoint-progress within N minutes; the other only surfaces process-level errors.

**Nit — Folder ids and search filter parameters are underspecified.** Item 17 (line 469) says a folder id is "the base64url of its directory prefix" without saying relative-to-root or absolute, and `/api/search`'s `folder`, `after`, and `before` (line 214) are not tied to that id format or given a date format or inclusivity. The two implementers produce mutually unintelligible clients.

**Nit — Media serving for tombstoned records is ambiguous.** Item 19 (line 479) says "verify the hash exists in a live record," but does not say whether a tombstoned photo's media 404s during the 30-day revival window (cache file still present) or serves, nor how a hash shared with a live duplicate behaves. One implementer enforces `deleted_at IS NULL`; the other serves any hash the indexer has ever seen.

**Nit — Duplicate "reporting" has no destination.** Non-Goals (line 54) says duplicates "are detected and reported; acting on them is deferred," but no endpoint, status field, or UI surface is named. One implementer adds a count to `/api/status`; the other produces nothing user-visible.

The document is strong on the identity/change-detection and degradation stories — those sections are unambiguous and internally consistent. The gaps cluster where a decision was deferred to a spike or left to the implementer's taste: the exact edit/re-link record mechanics, the cutover threshold, the API response contract, and the adapter wire format.
