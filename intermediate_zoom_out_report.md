## Ranked Findings

**1. [Blocker] The model-cutover mechanism should be re-architected, not patched — automated threshold cutover is the wrong altitude for a single-operator system.** (CUJ 8 line 108; pipeline line 205; worker line 449; NFR line 363; defaults table 582–591)
The accumulated record shows one subsystem generating at least seven unresolved decisions: the unpinned threshold (Stage 5 #4, D3, Stage 6), the `failed_perm`-in-the-denominator rule (Stage 6), re-embed job dedup and the single `embedded_at` column against per-model vectors (Stage 6), the `model_id` authority conflict (Stage 5 #5, Stage 6), the query-embedded-with-old-model trap (Y6), and the memory peak versus "search never goes dark" contradiction (Stage 5 #9, D7 — two NFR-level claims that cannot both hold). Consequence if patched decision-by-decision: the implementer writes and tests a migration state machine that will run roughly once every few years, with the recorded failure mode that a few percent of permanently-failing files stall cutover indefinitely while two vector sets coexist. The simpler architecture fits this system's ownership model exactly: the re-embed runs through the existing queue unchanged, `/api/status` reports new-model coverage, and **the owner initiates cutover** (config flip or one admin endpoint), accepting a brief announced search pause during matrix reload. That single decision deletes the threshold question, the accounting question, the job-dedup question, the ~920 MB double-residency, and the D7 contradiction — five specifications and one impossibility removed by choosing less machinery.

**2. [Blocker] The resident vector index has no refresh path — search silently serves a startup snapshot while the library and the embed queue grow.** (Line 205: "At startup (and at model cutover) all vectors … load"; `plaps/search.py` line 454; `plaps/app.py` line 489; coverage counters lines 189, 215, 474)
Missed by all three prior stages. The design specifies matrix loads at two moments only — process start and model cutover — but the steady state of this system is continuous: the scanner adds photos every pass and the embed worker writes new vectors for weeks after first run. Consequences: during the entire first embed (the exact window CUJ 1 and CUJ 4 describe, with the coverage line growing), search ranks only against photos embedded before process start — typically zero; after steady state, every newly indexed and embedded photo, and every tombstone, is invisible or wrongly visible until the next restart, which nothing in the design schedules. This also inverts the Stage 5 #1 fix: making the coverage line filter-scoped would report "search covers 50,000 of 150,000" while the searchable set is the startup snapshot — the line lies in the opposite direction from the one already recorded. The fix is small (append-and-swap on worker write, mask on tombstone; an immutable-array swap also solves the reader/thread tearing problem and is the same primitive cutover needs), but it is a genuine missing piece of the search subsystem's architecture, not a wording fix.

**3. [Blocker] The degradation story for the embedding dependency must be restated and the coverage line redesigned together — the fixes interact.** (Goals lines 38, 41; CUJ 4 and 6 lines 84, 96; pipeline line 205; NFR line 363)
D1 established that "search serves whatever is embedded" is unimplementable with the box down — text queries need the remote encoder — and D2 established that the latency claim ignores the mandatory remote round trip, which was never measured. The synthesis point the stages each held a slice of: fixing these in isolation produces a coverage line with a third undeclared state. After the honest restatement, the results view must distinguish *endpoint down*, *nothing embedded in this filter*, and *nothing matched* — and the Stage 5 #1 fix (filter-scoped counts) must land at the same time, or the line misleads in two of the three states. The YAGNI-correct fix is the restatement (search unavailable with a distinct error state; browsing, folders, and originals unaffected), not a local fallback encoder, which would add a second model dependency to avoid admitting the first.

**4. [Major] The identity subsystem conflates two different operations under the word "delete," and the collision with `UNIQUE(path)` leaves the most safety-relevant event in the system unimplementable as specified.** (CUJ 5 line 90; data model lines 167–193; scanner lines 197, 434)
Stage 6 established that "in-place edit deletes the old record and inserts a new one" cannot be a tombstone — a tombstoned row blocks the insert on `UNIQUE(path)` — and that what cascades to the old `photo_id`, vector row, and cache entries is unstated. The architecture-level view: the design has two distinct deletions — *vanish* (tombstone, revival window, guard, purge cascade) and *content-change-at-same-path* (record replacement that must bypass the tombstone path entirely, since the path must be freed) — and never separates them. Consequences: the implementer's choice (hard delete with cascade versus in-place row rewrite) silently decides whether the mass-delete guard and revival window apply to edited files at all, whether `/original/<photo_id>` links survive an edit, and whether the purge cascade (specified for cache but not vectors, D17) destroys the old embedding; `tests/test_scanner.py` as listed cannot be written until one pathway with one explicit cascade over vectors, all three cache variants, and jobs is chosen. A one-paragraph separation of the two operations closes Stage 5 #8, Stage 6's edit finding, D11, and D17 at once and states the guard's actual scope (vanish-only), so CUJ 7 is not read as covering bulk rewrites.

**5. [Major] The derived-artifact pipeline has three artifacts and a data model for two, and the four fixes the stages proposed in this area conflict with each other.** (Serving line 201; images line 439; jobs table lines 185–187; worker line 449)
The individual findings: screen-fit has no job kind, no per-stage column, and no owner (Stage 6); the embed-input choice — original bytes versus the cached 2048 px image, a ~10x LAN-transfer difference over 150K photos — is unclaimed (D4); both thumbnail variants are generated eagerly for a style toggle one user exercises one way (Stage 5 #7); lighttpd serving `/media/` directly from the hash-keyed cache was never weighed (D6). The interaction nobody assembled: if the embed input becomes the screen-fit image, the embed queue now depends on an artifact the design generates lazily in request threads — so screen-fit must become an eager job kind with its own column, which reopens the lazy-versus-eager question for the thumbnail variants; and lazy generation in turn conflicts with the static-alias option, which works cleanly only against a complete cache. Consequence: these four fixes cannot be applied independently; one decision — which artifacts are eager, which are lazy, and therefore what the jobs table and per-stage columns contain — must be made first, at the pipeline level rather than as four local patches.

**6. [Major] The client contract is the document's load-bearing architectural seam and does not exist.** (Overview line 13; API surface lines 209–218; api modules 461–479; settings lines 39, 72)
Stage 6 found the response bodies unspecified, the settings homeless, the folder-id and cursor encodings double-stated, and the search filter parameters untyped; D5 and S6 repeat the settings and naming gaps. At architecture altitude this is one gap, not six: the design justifies client-side rendering, the no-build frontend, proxy auth, and the whole API shape by repeated appeal to "the same API a future Android client would consume" (four near-verbatim occurrences, Y31), yet stops the specification at URL shapes. Consequence: the frontend itself — the actual, non-speculative client — cannot be built from this document; two implementers invent different photo cards and mutually unintelligible clients. The minimal fix is in the document's own spirit: specify the photo card fields, the error shape, one folder-id format, and put grid style and sort order in client-side localStorage (the YAGNI-minimal settings home for one user with one browser), which retires the Android framing as a justification rather than a scope commitment.

**7. [Major] The verification effort was spent on the wrong risks: the heavily spiked path was the cheap one, and the expensive uncertainties are simultaneously asserted as acceptance criteria.** (NFR line 363; CUJ 1 and 4 lines 66, 84; verification plan 599–600; spikes)
The X-Sendfile spike retired a milliseconds-scale local risk (and correctly so — it caught a silent zero-byte failure), while the genuinely uncertain quantities — production AI-box embed rate (only the dev box was measured, ~4.2 days per 150K, contradicting the stated 4–42 h), standalone text-embed latency (never measured), and folder-view query cost — remain unmeasured and are hard-coded into CUJs and the NFR (Stage 5 #6, D2, D9, D16). Consequence: CUJ 1 and CUJ 4 fail or get waived on real hardware, and folder view — the heaviest read path, a per-request recursive newest-date aggregation over 150K paths, with the brief's "cacheable per view" qualifier dropped during drafting — has no target and no stated approach. The fix is two measurements and one sentence (an in-process memoized tree invalidated on scan commit), not a redesign.

**8. [Major] The threat model is structural everywhere except the one channel that carries the entire library.** (Security line 222; configuration line 226; pipeline line 205; NFR line 362)
D8 stands alone at synthesis level because the rest of the security posture removes attack classes by construction: the design demands TLS before any photo is served past the LAN while streaming every original, base64 and unencrypted, to the AI box as ordinary operation. Consequence: one config requirement (`https://` required for `embedding.base_url`) or one written acceptance of LAN plaintext; as specified, the privacy NFR is selectively applied to the cheaper path.

**9. [Nit] Declared closure is not auditable, and three stages have now each falsified it independently.** (Line 58 vs. 226 — S1/Y1 — plus the cutover threshold, embed input, edit mechanics, guard arithmetic, jobs uniqueness, screen-fit ownership, settings home, and response bodies)
"Open Questions: none" and "tuning values are pinned" are contradicted by at least eight decisions the accumulated record found genuinely open, and S2 records that risk substance has no auditable home. Consequence: every downstream stage pays to re-discover the same unresolved set. A decision register (or an honest open-questions list) covering exactly the items in findings 1–5 is cheaper than scattered "resolved" claims that each new reviewer re-falsifies.

**10. [Nit] `error_kind`/`error_text` is a single slot per photo for four independent failure kinds.** (Data model lines 177, 193)
A photo with malformed EXIF that later fails thumbnailing or embedding overwrites its earlier error; `/api/status` error counts by kind then undercount, and the "per-stage failure modes" rationale is contradicted by the schema. One column pair per stage, or an errors table, matches the design's own per-stage reasoning.

## Verdict

The architecture survives the accumulated findings. The load-bearing decisions — in-place stat-pruned scanning, hash-based identity with one record per path, one process with one locked SQLite writer, SQLite as the only store, a content-hash-keyed derived cache, brute-force ranking over a resident matrix, proxy-terminated auth, no watcher, no queue, no Docker — are untouched by anything Stages 5–8 found, and no finding pushes toward any of the rejected machinery. Notably, the accumulated findings push toward *less* machinery than the document currently promises (owner-initiated cutover, lazy variants, client-side settings), which is the direction the design's own goals require; the document's one over-engineered mechanism is the automated cutover, and the recorded holes in it are symptoms of that, not separate defects.

Two things genuinely need to change rather than be worded better: the vector index needs an incremental refresh path (finding 2 — the only missing subsystem the stages found), and the delete semantics need to be separated into two operations with one cascade (finding 4). Everything else is a decision to be written down inside the existing structure. The pattern across all four stages is consistent: the document is strongest where it was forced to reason from a verified negative result or a stated hard problem (identity, media serving, the inotify rejection) and weakest in the subsystem attached to the one external dependency — availability, cutover, index freshness, and measurement all cluster on the embedding path — and in the seams it declared as contracts (the API, the pipeline stages) without specifying. The fixes implied by the earlier findings interact badly in exactly two places — coverage-line scope with the degradation restatement, and embed-input with lazy screen-fit and static serving — and both dissolve if made as the single decisions described in findings 3 and 5 rather than as the sum of their parts.
